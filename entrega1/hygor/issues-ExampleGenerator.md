## F1 ([#25234](https://github.com/OpenAPITools/openapi-generator/issues/25234)): [BUG] ExampleGenerator: generated numeric examples violate `maximum` (negative, without `minimum`) and ignore `exclusiveMinimum`/`exclusiveMaximum`

**Casos:** CT-EG-24 (integer e number), CT-EG-25; CTM-EG-01 passo 4.

#### Bug Report Checklist

- [x] Have you provided a full/minimal spec to reproduce the issue?
- [x] Have you validated the input using an OpenAPI validator?
- [x] Have you tested with the latest master to confirm the issue still exists?
- [x] Have you searched for related issues/PRs?
- [x] What's the actual output vs expected output?

##### Description

Examples generated by `ExampleGenerator` for numeric schemas are not valid instances of the schema in two situations:

1. Only `maximum` is set and it is negative. `randomNumber(min, max)` returns `random.nextDouble() * max`, which lies in `(max, 0]` when `max < 0`. With `maximum: -5` the generated example is `0` (integer) or `-0.4004...` (number).
2. `exclusiveMinimum` / `exclusiveMaximum` are never read. For `type: integer, minimum: 0, exclusiveMinimum: true`, the generated value is `random.nextDouble() + 0` truncated to `int`, which is always `0`.

The OpenAPI 3.0.3 Schema Object defines `example` as "an example of an instance for this schema". `maximum`/`exclusiveMinimum` follow JSON Schema Validation (wright-00, 5.2–5.5). The generated examples end up in HTML/Markdown docs and in server stubs (`JavaSpring`, `java-wiremock`, `aspnetcore`), where they fail validation against the spec they came from.

##### openapi-generator version

7.25.0 (also current `master`).

##### OpenAPI declaration file content or url

```yaml
openapi: 3.0.3
info: {title: repro, version: 1.0.0}
paths:
  /temperature:
    get:
      responses:
        '200':
          description: ok
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Reading'
components:
  schemas:
    Reading:
      type: object
      properties:
        celsius:
          type: integer
          maximum: -5
        level:
          type: integer
          minimum: 0
          exclusiveMinimum: true
```

##### Generation Details / Steps to reproduce

```
java -jar openapi-generator-cli.jar generate -g html -i repro.yaml -o out
```

Actual "Example data": `{"celsius" : 0, "level" : 0}`.
Expected: `celsius <= -5` and `level > 0`.

##### Suggest a fix

In `randomNumber`, when only `max` is set, use `max - random.nextDouble()` (or an offset below `max`). Read `getExclusiveMinimum()` / `getExclusiveMaximum()` (and `exclusiveMinimumValue` / `exclusiveMaximumValue` for 3.1), and nudge integer bounds by 1 when they are exclusive.

## F2 ([#25235](https://github.com/OpenAPITools/openapi-generator/issues/25235)): [BUG] ExampleGenerator: generated array examples ignore `minItems`

**Casos:** CT-EG-29; CTM-EG-01 passo 5.

##### Description

The length of a generated array example is `maxItems` (default 2, capped at 5). `minItems` is never read, so `minItems: 3` without `maxItems` produces a 2-item array, which is not a valid instance of the schema (JSON Schema Validation wright-00, 5.11).

##### openapi-generator version

7.25.0 (also current `master`).

##### OpenAPI declaration file content or url

```yaml
components:
  schemas:
    Reading:
      type: object
      properties:
        samples:
          type: array
          minItems: 3
          items:
            type: integer
            example: 7
```

(referenced from a response, same as the F1 spec)

##### Steps to reproduce

`generate -g html` → "Example data" shows `"samples" : [ 7, 7 ]`. Expected: at least 3 items.

##### Suggest a fix

`arrayLength = max(minItems ?: 0, min(maxItems ?: 2, 5))`. If `minItems > 5`, `minItems` should win over the memory cap, because an example that violates the schema is worse than a longer one.

## F3 ([#25236](https://github.com/OpenAPITools/openapi-generator/issues/25236)): [BUG] ExampleGenerator.generateFromResponseSchema treats the keys of an inline object `example` (java.util.Map) as media types

**Casos:** CT-EG-45 (não reproduz pela CLI; ver CTM-EG-01 passo 7).

##### Description

When `generateFromResponseSchema(statusCode, schema, produces)` gets an inline (non-`$ref`, non-array) schema whose `example` is a `java.util.Map`, the "primitive type" branch casts the example to `Map<String, Object>` and passes it as the `examples` argument of `generate(Map, List, Schema)`. That argument means `{mediaType -> example}`, so every key of the example becomes a `contentType` and every value becomes a separate example:

```java
Schema<Object> response = new ObjectSchema()
        .addProperty("id", new IntegerSchema())
        .addProperty("name", new StringSchema());
response.setExample(Map.of("id", 1, "name", "Rex"));

new ExampleGenerator(Map.of(), new OpenAPI())
        .generateFromResponseSchema("200", response, Set.of("application/json"));
// actual:   [{contentType=name, example="Rex", statusCode=200}, {contentType=id, example=1, statusCode=200}]
// expected: [{contentType=application/json, example={"id":1,"name":"Rex"}, statusCode=200}]
```

When the spec is read from a file, swagger-parser gives the example as a Jackson `ObjectNode`, not a `Map`, so the CLI does not hit this path. It affects programmatic use, such as custom generators or tools that build or transform the `OpenAPI` model with plain Java maps.

##### openapi-generator version

7.25.0 (also current `master`).

##### Suggest a fix

In `generateFromResponseSchema(Schema, Set)`, handle any non-null `example` (including `Map`) through `generate(Object, List)`, and use the `generate(Map, ...)` overloads only for the media-type map.

## F4 ([#25237](https://github.com/OpenAPITools/openapi-generator/issues/25237)): [BUG] ExampleGenerator returns the string "{}" (or null) for `type: object` schemas without `properties`

**Casos:** CT-EG-48, CT-EG-52; CTM-EG-01 passo 6.

##### Description

`resolvePropertyToExample` returns the Java string literal `"{}"` for an object schema without properties and for a `$ref` that cannot be resolved. `Json.pretty` then serializes it as a JSON **string** (`"metadata" : "{}"`) instead of an empty object (`"metadata" : { }`), so the example has the wrong type (JSON Schema Validation wright-00, 5.21).

The same happens one level up. For a top-level model `type: object` without `properties`, `resolveModelToExample` falls through to `return null`, and `generate(null, ["application/json"], "Anything")` returns the example `null`. Through the CLI this model gets unaliased first, so the operation simply has no example; only programmatic callers see `null`.

##### openapi-generator version

7.25.0 (also current `master`).

##### OpenAPI declaration file content or url

```yaml
components:
  schemas:
    Reading:
      type: object
      properties:
        metadata:
          type: object
```

##### Steps to reproduce

`generate -g html` → "Example data" shows `"metadata" : "{}"`. Expected: `"metadata" : { }`.

##### Suggest a fix

Return `new LinkedHashMap<>()` (an empty map) instead of the string `"{}"` in both branches of `resolvePropertyToExample`, and also for object schemas without properties in `resolveModelToExample`.
